# DParser grammars and generated syntax trees

Every `.g` file in this directory is a DParser grammar. Its matching `.absyn`
file defines the owning C++ syntax tree and visitors generated by
[`scripts/syngen.pl`](../scripts/syngen.pl). These two files are the source of
truth; generated C tables, C++ headers, and C++ implementations live under
`build/generated/parsers/`.

## Languages

`source.hpp` supplies the shared owning resolver and cumulative include budgets
used by the Unisel and Limeburg semantic loaders. Includes splice parsed AST
declarations, retaining each file's source spans. File loaders opt into relative
filesystem access and canonical cycle detection; text loaders use an explicit
host resolver. Defaults are 16 MiB, 128 document occurrences, and 32 include
levels. `origin` clauses preserve selection-rule provenance across canonical
serialization.

| Grammar | Syntax represented | Example |
| --- | --- | --- |
| `isa.g` | Infobank architectures, sections, registers, encodings, operations, nested values and semantic S-expressions | [`isa.isa`](examples/isa.isa) |
| `traceml.g` | The existing TraceML S-expression frontend: applications, symbols, and integers | [`traceml.trace`](examples/traceml.trace) |
| `tuner.g` | Normalized operator declarations and rewrite rules, terms, variables, `:where` and `:cost` clauses | [`tuner.tuner`](examples/tuner.tuner) |
| `limeburg.g` | BURS nonterminals, terminals, typed/recursive patterns, immediate bounds, costs, priorities, and explicit input trees | [`limeburg.limeburg`](examples/limeburg.limeburg) |
| `unisel.g` | Universal machine descriptions, registers, instructions, patterns, source graphs, outputs, dependencies, and constraints | [`unisel.umd`](examples/unisel.umd) |
| `schedrow.g` | Scheduling regions, instructions, explicit/implicit operands, dependencies, bundles, and machine-model metadata | [`schedrow.schedrow`](examples/schedrow.schedrow) |
| `regtl.g` | Register classes/aliases, inclusive live ranges, fixed/allowed/forbidden constraints, clobbers, spill slots, and sequential/parallel transfers | [`regtl.regtl`](examples/regtl.regtl) |
| `bin2bin.g` | ISA references, translation mappings, semantic rewrite rules, instruction streams, bytes, and explicit translation statuses | [`bin2bin.bin2bin`](examples/bin2bin.bin2bin) |
| `limestone.g` | Machine-independent modules and pipeline/target descriptions | [`limestone.limestone`](examples/limestone.limestone) |

Parsing constructs syntax. Symbol resolution, numeric range checks, type/effect
verification, target legality, and conversion to subsystem IRs belong to the
respective semantic adapters. Attribute nodes retain unknown metadata in source
order. An ISA legacy marker, for example, parses successfully even though
Metacode requires an architecture before it can build a usable target.

The ISA and TraceML subsystem APIs share these generated C tables. Tunah's
existing compiler continues to use EkippX, SExprTk, and DSLtk: `tuner.g` describes
the **post-preprocessing** syntax and provides a separate syntax-tree entry
point. Parsing a `:cost` clause preserves it; Tunah's current semantic compiler
still reports that extraction costs belong to `CostModel`. These grammars do
not expand macros, follow imports/includes, invoke solvers, or infer machine
properties. The D MachineIR package remains a separately built D implementation;
`machine-ir.g` provides the C++ textual machine-module syntax boundary.

Identifiers support underscores, dots, and hyphens. `%name` denotes a virtual
value/register (or a named scheduling instruction); `$name` denotes a physical
register in register-oriented languages. Pattern bindings use `?name`, with
Unisel also accepting `$name`. Machine-module immediates use `#7` and symbol/CFG
references use `@name`. Quoted strings keep their original quotes and escapes.
Limeburg distinguishes a bare pattern symbol from an explicit nullary
application such as `CONST()`.

ISA comments start with `#`; TraceML and tuner comments start with `;`.
Brace-oriented grammars accept `//` and non-nested `/* ... */` comments.
Limeburg, Unisel, Schedrow, and Bin2Bin additionally accept `#` comments.
Limestone and MachineIR use `;` for line comments, matching the pipeline's emitted
text. Their metadata assignments and instructions do not require semicolons.
RegTL reserves `#` for immediates. All line-comment forms work at end of file.

## Build and use

Perl 5 with its core modules and the vendored DParser are sufficient for
generation; no additional Perl packages are required.

```sh
cmake -S . -B build
cmake --build build -j 2
ctest --test-dir build --output-on-failure
```

`limestone-generate-parsers` generates all ten table/AST pairs.
`limestone_parser_tables` owns the generated C tables.
Link **`limestone_parsers`** to use the typed parsing APIs; it exports the source
and generated include directories while keeping DParser headers private.

```cpp
#include "parsers/tuner_ast.hpp"

auto result = limestone::syntax::tuner::parse(
  "(operator add 2) (rule zero (add ?x 0) ?x)", "simplify.tuner");
if (!result) {
  // result.error().code and result.error().message describe the failure.
  return;
}
auto document = std::move(result.value());
```

Headers are named `parsers/<grammar>_ast.hpp`. Namespaces are
`limestone::syntax::<grammar>`; `machine-ir` becomes `machine_ir`.
Each namespace has a `parse(input, filename, limits)` function returning
`Result<std::unique_ptr<Document>>`. A tree owns its token spellings, filenames,
and child nodes and can outlive the input string and parser. Sum types use
variants of owning pointers; optional children are nullable pointers; repeated
children are vectors in source order.

Every node carries a `SourceSpan` with its filename and exclusive-end byte
positions. Lines and columns are one-based, and columns count bytes. Invalid
syntax and unresolved ambiguity return source-located `Parse` errors.
Grammar/schema cardinality mismatches return `Internal` errors instead of
silently dropping children. Parser instances and AST ownership are local to
each call.

`ParseLimits` defaults to 16 MiB of input, one million parse-tree nodes, and
depth 512. The byte limit and embedded-NUL rejection are checked before DParser;
node/depth limits are checked on its completed tree before AST construction.
These are input/tree bounds, not preemptive time or allocation limits inside
the vendored GLR runtime.

## Visitors

Each schema generates `Node`, `Kind`, concrete nodes, `Visitor`, `ConstVisitor`,
`RecursiveVisitor`, and `ConstRecursiveVisitor`. `accept` dispatches to a
concrete node's visitor overload. Ordinary visitors default to the base-node
overload and do not recurse. Recursive visitors visit all owning children in
schema/source order, including the active sum alternative. Const walkers
explicitly propagate constness to pointed-to nodes.

```cpp
struct Variables : limestone::syntax::tuner::ConstRecursiveVisitor {
  std::vector<std::string> names;
  void visit(const limestone::syntax::tuner::Variable& variable) override {
    names.push_back(variable.value);
  }
};
Variables variables;
std::as_const(*document).accept(variables);
```

Override `enter(Node&)`/`enter(const Node&)` and `leave` for generic pre/post-order
walks. Returning false from `enter` prunes that node's children and skips its
`leave` call. Mutable visitors may edit token values or owning child fields;
source spans continue to describe the original input. Syntax trees are intended
to be owned through their pointers.

## `.absyn` schema language

```text
namespace example::syntax;
parser example;
root Document;

node Document { Declaration* declarations; }
sum Declaration = Definition | Import;
node Definition { Ident name; Expr body; }
node Import { String path; }
sum Expr = Ident | Application;
node Application { Ident opcode; Expr* arguments; }
token Ident;
token String;
```

- `namespace`, `parser`, and `root` are required, in that order. `parser` names
  the C table identifier passed to DParser's `-i` option.
- `node Name { ... }` defines a composite matching grammar production `Name`.
  A field `Type name;` captures exactly one shallow `Type` child.
- `Type? name;` captures zero or one; `Type* name;` captures all matching children.
  DParser's synthetic EBNF nodes are flattened; named grammar productions remain
  capture boundaries.
- `@N` selects a zero-based occurrence when a production has several children
  of the same type. A repeated capture `Type* rest @N;` selects the suffix
  beginning at occurrence `N`. For example:
  `node TreeNode { Ref result @0; Ref* operands @1; }`.
- `sum Name = A | B;` captures exactly one active child as a typed variant.
- `token Name;` copies the production's exact token spelling into `value`.
- Forward references and recursive nodes are supported. Comments may use `#`,
  `//`, or `/* ... */`. C++ keywords, reserved identifiers, duplicate declarations,
  unknown types, and overlapping captures are rejected with schema coordinates.

Generate or validate a pair independently:

```sh
perl scripts/syngen.pl --grammar parsers/tuner.g --check parsers/tuner.absyn
perl scripts/syngen.pl --grammar parsers/tuner.g \
  --header build/generated/parsers/tuner_ast.hpp \
  --source build/generated/parsers/tuner_ast.cpp parsers/tuner.absyn
```

Output directories must exist. `--grammar` verifies that the root is the first
production, that all named productions except `whitespace` have AST definitions,
and that all grammar-child relationships are mapped. Validation finishes before
output replacement, and each output file is replaced atomically. Output contains
no timestamps or absolute input paths.

## Regression coverage

`tests/parsers.cpp` exercises all ten examples, malformed syntax for every
grammar, source spans, owned lifetimes, mutable/const traversal and pruning,
comment/string boundaries, limits, and pipeline-output ingestion. It also parses
the 23 architecture descriptions and the legacy marker in the Infobank and all
239 rules in the supplied tuner corpus. `tests/syngen.pl` covers deterministic
generation, schema/grammar validation, indexed captures, diagnostics, and
preservation of outputs on invalid specifications.
